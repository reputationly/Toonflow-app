## 一、开源真实性审计

**结论：是真开源，且是本地优先的。** 除模型 API 外没有隐藏的远端依赖、许可证服务器或遥测。有两个需要注意的点（License 附加条款、vm2 沙箱）。

### 1.1 源码完整性

| 部分 | 位置 | 状态 |
| --- | --- | --- |
| 后端 | 本仓 `src/`（211 个 `.ts`） | ✅ 完整源码，Express 5 + knex/SQLite |
| Electron 主进程 | `scripts/main.ts` | ✅ 完整源码 |
| Agent 提示词 | `data/skills/`（215 个 `.md`） | ✅ 明文 Markdown |
| 供应商适配 | `data/vendor/*.ts`（11 个） | ✅ 明文 TypeScript |
| 前端 | `data/web/index.html`（26 MB） | ⚠️ 本仓内仅编译产物 |

前端源码在**独立仓库** [Toonflow-web](https://github.com/HBAI-Ltd/Toonflow-web)（Vue 3 + Vite，382⭐）。

**同步性核验**：web 仓最后提交 `9c4cb0e`（2026-06-09），app 仓内置的 `data/web` 对应 v1.1.8（2026-06-08 发布）——**两者同步，不存在"留一手"**。

两个"非源码"文件，均非黑盒：

- `data/serve/app.js`（10 MB）—— 后端 esbuild 打包产物，`yarn build` 可完全复现（`scripts/build.ts` 中 `minify: false`）。提交进仓库只为 `yarn start` 免编译。
- `data/models/all-MiniLM-L6-v2/onnx/model_fp16.onnx` —— 本地向量模型权重，HuggingFace 开源模型。

### 1.2 远端调用清单

全仓库扫描（含 10 MB 后端 bundle 与 26 MB 前端 bundle）后，非模型类外链仅三处：

**未发现**：埋点 / 遥测 / 账号系统 / 激活码 / license 校验 / 云端配额。
（grep 关键词 `激活码|activation|licenseKey|vip|quota|授权码` 零命中；前端 bundle 域名扫描无任何统计服务。）

### 1.3 本地化验证

- **供应商默认全关**：`src/lib/initDB.ts:568-613` 中 8 个内置供应商均为 `enable: 0`，无内置 API Key。
- **登录纯本地**：`src/routes/login/login.ts:31` 直接查本地 SQLite `o_user` 表比对（明文密码，`admin/admin123`）。
- **向量检索离线**：`src/utils/agent/embedding.ts:29` 显式设置 `transformersEnv.allowRemoteModels = false`，模型文件缺失直接抛错，绝不联网拉取。

### 1.4 两个风险点

#### ⚠️ License 不是纯 Apache-2.0

`LICENSE:206` 起附加「补充协议」：

- 分发给 **2 个及以上独立第三方**必须取得 HBAI-Ltd 书面商业授权
- 按年销售额阶梯收费（<¥10 万免费 → ¥5k / ¥20k / ¥80k / 面议）
- 不得移除或修改版权标识
- 永久免费场景：个人学习研究、二次开发内部自用、≤5 个法人联合运营内部使用
- 历史用户：v1.0.8 之前基于 AGPL-3.0 的使用不受追溯

**OSI 意义上不算纯开源许可**，属于"源码可得 + 商业附加条款"。

> 另注：web 仓 README 徽章标 AGPL，但仓库 license 字段是 Apache-2.0，存在不一致。商用前建议向 `ltlctools@outlook.com` 确认。

#### ⚠️ 可编程供应商使用 vm2 沙箱

`src/utils/vm.ts:1` 使用 `vm2`——该库已被作者废弃且存在公开的沙箱逃逸漏洞。这意味着"在设置中心写 TypeScript 并即时生效"这一特性的隔离性不可信，等价于任意代码执行。

- 单机自用：无实质影响
- **多租户 / 对外提供服务：这是致命风险**，必须替换（如 `isolated-vm`）或彻底关闭该入口

### 1.5 审计范围声明

本次审计对象是**仓库源码**，未反编译 GitHub Releases 中的安装包，也未逐行审阅 26 MB 的压缩前端产物（仅做了外链域名扫描）。

### 四维结论

**画布** —— Toonflow 的最强差异化。11 个项目中仅 Toonflow、novelvids（294⭐）、NodeTool（非垂类）有真无限画布，头部项目全是线性流水线或看板。

**智能体** —— 已是标配，但分两派：内建 agent（Toonflow / ViMax / huobao）vs 外置 agent（OpenMontage / NodeTool，把自己变成工具集让 coding agent 驱动）。Toonflow 的三层架构 + 本地 ONNX 跨会话记忆在内建派里做得较深。

**MCP** —— **整个短剧垂类近乎空白**，仅 NodeTool 一家。MCP 生态集中在旁支（ComfyUI MCP server、剪映草稿 CLI）。**这是 Toonflow 最明显的短板，也是空位。**

**网页端** —— Toonflow **已经是网页端**。`src/app.ts:143` 用 `express.static` 托管 `data/web`，Electron 只是外壳；README 已有 Docker 与 PM2 集群方案。缺的不是 Web 形态，而是多用户能力：单张 `o_user` 表、明文密码、无租户隔离、无权限体系。

### 定位小结

Toonflow 在垂类中 star 数第一（56k 的 OpenMontage 严格说是编排框架而非产品），**唯一同时具备"无限画布 + 深度 agent + 桌面/Web 双形态 + 可商用 License"**。主要威胁：① ArcReel/huobao 迭代更快（前端源码停在 6 月）；② MCP 缺位；③ 补充商业条款会劝退部分商用分发需求。

## 三、仓库结构与定制开发

### 3.1 两个仓库

| 仓库 | 内容 | License |
| --- | --- | --- |
| **Toonflow-app** | 后端 `src/` + Electron `scripts/` + 运行时 `data/` + 前端产物 `data/web/` | Apache-2.0 + 商业补充条款 |
| **Toonflow-web** | 前端 Vue 3 源码 | 仓库标 Apache-2.0，README 徽章标 AGPL ⚠️ |

#### L1 · 加后端接口

`src/routes/` 是**文件即路由**，由 `src/core.ts` 扫描自动生成 `src/router.ts`：

| 文件 | 生成路径 |
| --- | --- |
| `src/routes/foo/bar.ts` | `/api/foo/bar` |
| `src/routes/foo/index.ts` | `/api/foo` |
| `src/routes/foo/[id].ts` | `/api/foo/:id` |
| `src/routes/foo/[...rest].ts` | `/api/foo/*` |

写法参考 `src/routes/login/login.ts`：导出 `express.Router()`，用 `validateFields({...})`（zod）校验，`success()/error()` 统一响应，`u.db("表名")` 走 knex。

**所有 `/api/*` 默认过 JWT 中间件**（`src/app.ts:156-170`），白名单仅 `/api/login/login`。

建表在 `src/lib/initDB.ts`，增量修复在 `src/lib/fixDB.ts`。

## 四、本地调试模式

**不需要打包**。项目提供 4 种模式：

| 命令 | 后端 | 前端 | 适合 |
| --- | --- | --- | --- |
| `yarn dev` | tsx 源码，**固定 10588**，已带 `--inspect` | 无 | 纯写接口 / Postman 调 API |
| `yarn dev:gui` | tsx 源码，随机端口 | `data/web` 打包产物 | 只改后端但想看真实界面 |
| **`yarn dev:gui-vite`** | tsx 源码，随机端口 | vite 热更新 | **全栈开发，主力模式** |
| `yarn start` | `data/serve/app.js` | 打包产物 | 验证构建产物 / 服务器部署 |

### 4.1 主力模式：dev:gui-vite

```bash
# 终端 1 —— 前端
cd Toonflow-web && yarn dev          # vite dev server，50188

# 终端 2 —— 后端 + Electron 外壳
cd Toonflow-app && yarn dev:gui-vite
```

原理：`VITE_DEV=1` 使 `scripts/main.ts:150` 让 Electron 直接 `loadURL("http://localhost:50188")` 加载 vite 开发服务器；同时 `scripts/main.ts:180` 判断非打包环境时后端加载 **`src/app.ts` 源码**（靠 `-r tsx` 的 require 钩子），而非 `data/serve/app.js`。

效果：前端改 `.vue` 热更新，后端改 `.ts` 由 electronmon 重启，`toonflow://` 协议（窗口控制、DevTools、系统语言）全部可用，行为与打包产物一致。

### 4.2 调试手段

**后端断点** —— `yarn dev` 已带 `--inspect`（inspector 在 9229）。`.vscode/launch.json` 已配置好 attach。
`dev:gui` 系列未带，需要时改 `package.json`：`electronmon -r tsx --inspect=9230 scripts/main.ts`。

**前端 DevTools** —— 窗口是 `frame: false` 且 `removeMenu()`（`scripts/main.ts:129-138`），**F12 与菜单栏都不可用**。两个办法：应用内有触发 `toonflow://opendevtool` 的入口（`scripts/main.ts:230`）；或调试期间在 `createMainWindow` 的 `ready-to-show` 回调里加 `win.webContents.openDevTools()`。

**LLM 调用排查** —— `yarn debug:ai` 启动 `@ai-sdk/devtools`，可查看每次请求的完整 messages、tool call、token 消耗。Agent 行为异常时优先看这个。

**日志** —— `src/err.ts` 注册了 `unhandledRejection` / `uncaughtException` 全局兜底，打印完整堆栈与序列化详情。供应商脚本可调沙箱注入的 `logger()`，输出带 `【VM】` 前缀。

**类型检查** —— `yarn lint`（`tsc --noEmit`）。

**存活探针** —— `GET /api/test` 返回 `"ok"`（`src/routes/test/test.ts`），但同样过 JWT，无 token 返回 401——收到 401 本身即说明服务已启动。

### 5.2 步骤与问题

#### ① 安装 yarn

```bash
npm i -g yarn     # → 1.22.22
```

> 注：`package.json` 中 `packageManager: "yarn@1.0.0"` 是个可疑的版本号（yarn 1.0.0 是 2017 年的版本）。本机未装 corepack，因此该字段不会被强制执行，无影响。若你的环境启用了 corepack，需注意它可能尝试拉取 yarn 1.0.0。

#### ② 后端依赖安装失败 —— Node 版本不兼容

```
error better-sqlite3@12.9.0: The engine "node" is incompatible with this module.
Expected version "20.x || 22.x || 23.x || 24.x || 25.x". Got "26.3.1"
```

Node 26 太新。项目 CI 使用 Node 24（`.github/workflows/release.yml` 的 `NODE_VERSION: "24"`）。

> ⚠️ **教训**：首次安装时用了 `yarn install | tail -40`，管道吞掉了 yarn 的退出码，导致误判为成功（`exit 0`）。验证安装结果时不要用管道，或使用 `set -o pipefail` / `${PIPESTATUS[0]}`。

#### ③ 安装 Node 24 + fnm

先用 brew 装 keg-only 的 node@24 应急，随后引入 fnm 做长期管理：

```bash
brew install node@24     # → v24.20.0，keg-only，不影响默认 node
brew install fnm         # → 1.39.0
```

写入 shell 配置（**已备份原文件到 `~/.zshrc.bak-20260904-150804`**）：

```bash
# fnm (Node 版本管理) —— --use-on-cd 让 cd 进带 .nvmrc 的目录时自动切换
eval "$(fnm env --use-on-cd --shell zsh)"
```

```bash
fnm install 24           # → v24.20.0
fnm alias system default # 关键：把默认版本改回系统的 node 26
```

> **为什么要 `fnm alias system default`**：fnm 首次安装会自动把新版本设为 default，这会让所有新终端的默认 Node 从 26 变成 24，影响机器上的其他项目。改回 `system` 后，只有带 `.nvmrc` 的目录才切换到 24。

两个仓库根目录各放一个 `.nvmrc`，内容为 `24`。

## 六、踩坑清单

### ⚠️ 坑 1：两种调试模式的原生模块不能共存

`better-sqlite3` 当前编译为 Electron ABI（143），**`yarn dev`（Node 模式）会崩溃**（已实测确认）。切换需重编译：

```bash
# 切到 Node 模式（yarn dev / 浏览器调试）
yarn install --force

# 切回 Electron 模式（yarn dev:gui-vite）
npx @electron/rebuild -f -w better-sqlite3 -v 40.8.5
```

> 用 `@electron/rebuild` 而非旧的 `electron-rebuild`：后者已从 devDependencies 移除
> （它是 `lzma-native` 的唯一来源，会导致 macOS Intel 交叉构建时 node-gyp 因
> Python 3.12 移除 `distutils` 而失败）。`@electron/rebuild` 由 electron-builder
> 自带，无需单独安装。

以上两条均经过实测往返验证。两个反面教训：

- **`@electron/rebuild` 没有 `--node` 标志**（`npx @electron/rebuild --help` 可确认），不要臆造。
- **不要用 `npm rebuild better-sqlite3` 单独重建**。它确实能换回 Node ABI（不再报 `NODE_MODULE_VERSION`），但会让 native 模块之间状态不一致，启动时崩在：
  ```
  node::RemoveEnvironmentCleanupHook ... Assertion failed: (env) != nullptr
  ```
  必须用 `yarn install --force` 全量重建（实测仅耗时约 1.5 秒，且不会改动 `yarn.lock`）。

主力用 `dev:gui-vite` 就保持现状，仅在需要裸调 API 时切回。

### ⚠️ 坑 2：Electron 模式和 Node 模式使用不同的数据目录

`src/utils/getPath.ts` 只判断 `process.versions.electron` 是否存在，**不判断是否打包**：

| 模式 | 数据目录 |
| --- | --- |
| `yarn dev`（Node） | `<仓库>/data/` |
| `yarn dev:gui*`（Electron，未打包） | `~/Library/Application Support/**Electron**/data/` |
| 打包后的应用 | `~/Library/Application Support/**ToonFlow**/data/` |

> 开发环境路径中是 `Electron` 而非 `toonflow`——因为未打包时 Electron 的 app name 取默认值。打包后 electron-builder 设置 `productName: ToonFlow` 才会变。

**后果**：两种模式下配置的模型供应商、创建的项目完全不互通。启动日志会打印 `数据库目录: xxx` 和 `文件目录: xxx`，以日志为准。

同理，**仓库里修改 `data/skills/*.md` 在 Electron 模式下不生效**——`scripts/main.ts` 的 `initializeData()` 仅在版本号变大时才从安装包覆盖到 userData。调 Prompt 时要么直接改 userData 下的副本，要么临时提升 `package.json` 的 version。

### ⚠️ 坑 3：`router.ts` 是生成物，且只在 NODE_ENV=dev 时重新生成

`src/router.ts` 与 `src/types/database.d.ts` 均由脚本生成，且 `.gitignore` 中已列出（但 `database.d.ts` 因已被跟踪，ignore 规则对其无效）。

生成时机：

- `src/app.ts:53` —— `if (process.env.NODE_ENV == "dev") await buildRoute();`
- `src/utils/db.ts:40` —— `if (process.env.NODE_ENV == "dev") initKnexType(db);`

而 `src/env.ts:12` 的逻辑是：**未显式设置 NODE_ENV 时，Electron 环境默认设为 `prod`**。因此：

| 模式 | NODE_ENV | 是否重新生成 router.ts |
| --- | --- | --- |
| `yarn dev` | `dev` | ✅ |
| `yarn dev:gui-vite` | **`prod`** | ❌ |

**结论：新增路由文件或改表后，必须跑一次 `yarn dev`（Node 模式）来重新生成，`dev:gui-vite` 永远不会生成。**

另：`router.ts` 与 `database.d.ts` 虽然写在 `.gitignore` 里，但**已经被 git 跟踪**
（gitignore 对已跟踪文件无效），干净检出里它们是存在的，所以 CI 直接 `yarn build` / `yarn dist:*`
不会失败。只有当你手动删掉它们、或在从未生成过的新环境里删档重来时，才需要先 `yarn dev` 一次。

`nodemon.json` 已把 `router.ts` 和 `database.d.ts` 加入 ignore（防止生成动作触发无限重启），所以生成后不会自动热重载，手动 `rs` 或重启即可。

### ⚠️ 坑 4：Electron 模式下后端是随机端口

`scripts/main.ts:186` 调用 `mod.default(true)` 即 `randomPort: true`，端口通过 `toonflow://getappurl` 协议告知前端。

- 不要 hardcode 10588
- **不要同时运行 `yarn dev` 和 `yarn dev:gui-vite`**：前者占用 10588，后者前端从协议拿到另一个端口，极易看串

### ⚠️ 坑 5：默认凭据与安全

- `admin` / `admin123`，**明文**存于 SQLite 的 `o_user` 表（`src/routes/login/login.ts:31` 直接字符串比对，无哈希）
- JWT 密钥存在 `o_setting` 表的 `tokenKey`
- 对外部署前务必修改密码，建议加 bcrypt
- `vm2` 沙箱不可信（见 [1.4](#-可编程供应商使用-vm2-沙箱)）

### 📝 附：正常的 git 噪音

运行应用后 `git status` 会出现：

```
 M data/vendor/grsai.ts, null.ts, volcengineSd2.ts   ← 纯 CRLF/LF 换行符差异
 M src/types/database.d.ts                            ← 自动重新生成
```

- vendor 三个文件：应用启动时以 CRLF 重写造成，`git diff --ignore-cr-at-eol` 验证内容完全一致，每次启动都会复现，可忽略
- `database.d.ts`：实质变化仅一行——去掉了 `o_modelPrompt.prompt` 字段。全库 grep 确认无任何代码引用该字段，是上游遗留的过期类型，无影响

## 七、接入自建 New API 供应商（实录）

**结论：接一个新供应商只需要写一个 ts 文件，不用改任何源码。**

### 7.1 加载机制

```
<数据目录>/vendor/<id>.ts
  → src/utils/vendor.ts getCode() 读文件
  → sucrase 转译 TS → JS
  → src/utils/vm.ts 在 vm2 沙箱执行
  → 取 exports.vendor / textRequest / imageRequest / videoRequest / ttsRequest
```

注册信息存在 `o_vendorConfig` 表（`id` / `inputValues` / `models` / `enable`）。最终模型列表 = **代码里的 `vendor.models`** 与 **DB `models` 列**（界面手动添加的）按 `modelName` 合并去重。

关键点：

- **API Key 不写进 ts**，存在 `o_vendorConfig.inputValues`，由界面填写
- 声明 `version: "3.0"` 可拿到现代的 `referenceList` 入参结构；`< 2.0` 会被 `ai.ts:221` 降级成扁平的 `imageBase64`
- 运行时 `config.mode` 是**单个字符串**，尽管类型签名写的是 `VideoMode[]`
- `imageRequest`/`videoRequest` 返回 URL 即可，`ai.ts:258` 会自动下载转 base64
- 沙箱内 `Buffer`、`FormData`、`axios`、`pollTask` 均可用（已实测）

### 7.2 New API 端点契约（对 `maas.ovaijisuan.com` 实测）

| 用途 | 端点 | 格式 |
| --- | --- | --- |
| 文本 | `POST /v1/chat/completions` | OpenAI 兼容 |
| 文生图 | `POST /v1/images/generations` | JSON，同步返回 `data[0].url` |
| 图生图 | `POST /v1/images/edits` | **multipart**，同步返回 `data[0].url` |
| 图生图（异步） | `POST /v1/images/edits` + `"async": true` | JSON，返回 `{ id: task_id }`，需轮询 |
| 视频提交 | `POST /v1/video/generations` | JSON → `{ task_id }` |
| 视频查询 | `GET /v1/video/generations/{task_id}` | → `{ data: { status, result_url } }` |

#### 图生图的两条路（都可用，本供应商选了同步 multipart）

New API 对图片输入的处理**按同步/异步分流**，这是设计如此，不是 bug：

| 路径 | 图片入参 | 结果 |
| --- | --- | --- |
| 同步 `POST /images/generations` + JSON `image`/`images` | ❌ 不接受 | 报 `[Errno 2] No such file or directory: ''`。该端点在异步转换时被强制设为 `t2i`，同步链路同样不收图 |
| 同步 `POST /images/edits` + **multipart** | ✅ | 19.8s 直接返回 `data[0].url` |
| 异步 `POST /images/edits` + JSON + `"async": true` | ✅ | 31s，返回 `{id: task_id}`，轮询 `GET /images/generations/{task_id}` 拿 `data[0].url` |

原因在 `middleware/image_async_adapter.go`：该中间件只负责识别 `async` 开关，
**同步请求原样放行**。它刻意不解析同步 multipart 的 body——注释里说明了两点代价：
几 MB 的图会落一次临时盘，且 `ParseMultipartForm` 消费 body 后
`UnmarshalBodyReusable` 只能拿到 EOF，同步 edits 会直接 400。
只有异步分支才会调 `imageInputsFrom()`，那里才从 JSON 的 `raw["image"]` / `raw["images"]` 取图
（`middleware/image_async_adapter.go:269-270`）。

本供应商选**同步 multipart**：一次往返、无需轮询、实测更快。

视频状态值：`IN_PROGRESS` / `SUCCESS` / `FAILURE`，成功时地址在 `data.result_url`。
视频**没有** DELETE 端点（只有图像有），任务提交后无法取消。

### 7.3 视频模式映射

模式由 `metadata.task_type` 显式指定，帧图走**顶层 `images` 数组**：

| Toonflow 模式 | task_type | 图片参数 |
| --- | --- | --- |
| 文生视频 | `t2v` | 无 |
| 单图/首帧 | `i2v` | `images=[首帧]` |
| 首尾帧 | `flf2v` | `images=[首帧, 尾帧]`（少于 2 张报错） |
| 仅尾帧 | `l2va` | `images=[尾帧]` |
| 参考图 | `r2va` | `metadata.src_ref_images=[...]` |

`*-ref2va` 系列只认 `metadata.src_ref_images`，传顶层 `image` 无效。

### 7.4 模型规格（用非法参数探测得到，400 报错不消耗积分）

| 模型 | 支持时长（秒） | 分辨率档位 |
| --- | --- | --- |
| `minimax-h3-ref2va` | 4–15 | 480p / 768p |
| `minimax-h3-fast-ref2va` | 10–15 | 480p / 768p |
| `minimax-h3-fl2va` | 5–15（i2v 模式 4–15） | 480p / 768p |
| `minimax-h3-fast-fl2va` | 10–15 | 480p / 768p |
| `ltx2.5-hd` | 5–15 | 544p / 704p / 1080p / 2k |

> 💡 **探测技巧**：故意传 `duration: 1`，报错信息会直接列出全部合法值，且不产生费用。
> ⚠️ 但 `ltx2.5-hd` **不校验分辨率**——传非法宽高会直接开跑真实任务（实测冻结 102739 积分）。

### 7.5 安装步骤

供应商文件：`data/vendor/ovaijisuan.ts`（本仓已提交，可作为其他 New API 部署的模板）。

推荐走应用 API 安装（会自动通过 `addVendor.ts` 的 zod 严格校验并 `writeCode()` 落盘）：

### 7.6 TTS：Toonflow v1.1.8 尚未接线（暂不实现）

调研结论：**TTS 配音在 Toonflow v1.1.8 里是个半成品功能**，脚手架齐全但一根线都没接。

| 检查项 | 结果 |
| --- | --- |
| 前端 TTS / 配音 组件 | 0 个（仅资产上一个名为「音色」的自由文本字段） |
| 后端调用 `Ai.Audio` / `AiAudio` 的路由 | 0 个（类存在于 `src/utils/ai.ts`，全仓库无调用方） |
| 12 个内置供应商声明的 tts 模型 | 0 个；`ttsRequest` 全为空桩（仅 `vidu.ts` 主动抛错） |
| `o_agentDeploy` 的 `ttsDubbing` 槽位 | `disabled: 1` |
| `addVendor` / `addVendorModel` / `upVendorModel` 的 zod | 只接受 `text`/`image`/`video`，**会拒绝 `type: "tts"`** |

已存在的脚手架：`TTSModel` / `TTSConfig` 类型、`AiAudio` 类、`ttsRequest` 钩子、Agent 槽位。
要真正可用需要：改 3 处 zod 加 tts 分支 + 启用 `ttsDubbing` + 新增后端配音路由 + 前端音色选择/试听 UI（跨两个仓库）。

#### 上游 TTS 契约（已实测，留待将来接线时直接用）

端点：`POST /v1/audio/speech`（OpenAI 兼容，**同步返回二进制音频**，无需轮询）

| 模型 | 音色参数 | 实测 |
| --- | --- | --- |
| **`moss-voicegen`** | `instructions` = **自然语言音色描述**，如 `"a cold, menacing male villain voice, low pitch, Mandarin Chinese"` | ✅ HTTP 200，`audio/wav`，24kHz 单声道 16bit PCM，6–10s，约 130–180 KB |
| `indextts-2.5` | `voice` = **参考音频**（URL / data-uri），音色克隆 | ⚠️ 需自备每角色音频样本 |

- `speed`（如 `1.2`）与 `response_format`（`wav`）均实测被接受
- 不传 `instructions` 时 `moss-voicegen` 报错：`requires 'instructions' (natural language voice description...)`
- 不传参考音时 `indextts-2.5` 报错：`音色是一段参考音频而非预设名：voice 请传音频 URL / data-uri / task: 引用`
- 返回是裸二进制，`ttsRequest` 里需 `Buffer.from(res.data).toString("base64")` 拼成
  `data:audio/wav;base64,...` 返回——`oss.writeFile()`（`src/utils/oss.ts:154`）会自动剥前缀解码

**选型建议**：`moss-voicegen` 与 Toonflow 的 `TTSModel.voices: [{title, voice}]` 结构天然契合
（`title` 填中文音色名，`voice` 填英文音色描述），开箱即用无需素材；
`indextts-2.5` 留给后期做「角色音色跨集一致性」。

> 这也是 Toonflow 对比 lumenx（CosyVoice / Qwen3-TTS）、ArcReel 的一个真实功能短板。

```json
}
```

`type` 四种：`zip`（增量包）、`windows` / `macos` / `linux`（完整安装包）。

| 版本差异 | 行为 |
| --- | --- |
| Major / Minor | 找平台对应的安装包项，仅提示「请在浏览器手动下载安装」，不自动装 |
| Patch | 找 `zip` 项，**自动热更新**：下载 → 解压到 `data/temp/` → `cpSync` 覆盖整个 `data/` → 重启 |

> ⚠️ 热更新直接覆盖 `data/`，包括 `vendor/`。用上游的增量包会**冲掉你自定义的供应商 ts**；
> 自建分发源后此问题消失（增量包由你自己的 CI 从你自己的仓库生成）。

### 8.3 改造为自建 R2 分发

**后端**：`src/routes/setting/about/checkUpdate.ts` 顶部新增

```ts
const DEFAULT_MANIFEST_URL = process.env.UPDATE_MANIFEST_URL || "https://<你的R2公开域名>/update.json";
```

清单地址支持环境变量覆盖，私有化部署可各自指向自己的桶，无需改代码重新打包。

**前端无需改动**：`about.vue` 的 `updateSources` 里 `github`/`gitee`/`atomgit` 本就是
`disabled: true`，界面上实际只有一个可用源。`source` 枚举保持不变（它只是清单 `data`
对象里的键名，不是真正的「渠道」），这样不破坏既有前端产物的兼容性。

**CI**：`release.yml` 新增 `publish-r2` job（10 步），在 6 个平台包构建完成后：

1. 检出 + `yarn install`（带 `ELECTRON_SKIP_BINARY_DOWNLOAD=1`，省 ~100MB）
2. `yarn build` 产出 `data/serve/app.js`
3. 下载全部平台 artifact
4. 打增量包 `latest.zip`
5. 生成 `update.json`
6. `aws s3 cp` 上传到 R2（R2 兼容 S3 API，runner 自带 aws cli）

需要配置：

| 类型 | 名称 |
| --- | --- |
| Secrets | `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET` |
| Variables | `R2_PUBLIC_BASE`（公开访问地址，不带结尾斜杠） |

R2 上的布局：

```
<bucket>/update.json              ← 清单，no-cache，客户端固定读这个
<bucket>/1.2.0/latest.zip         ← 增量包
<bucket>/1.2.0/*.exe / *.dmg / *.AppImage   ← 按版本归档的安装包
```

### 8.4 三个实现要点

**① 增量包的根目录必须是 `data/` 的内容，不是 `data/` 本身。**
`downloadApp.ts` 解压到 `data/temp/` 后 `cpSync(temp, data)`，若压缩包里多一层 `data/`
会变成 `data/data/serve`。所以用 `cd data && zip -r ../latest.zip .`。
实测根条目为 `assets/ modelPrompt/ serve/ skills/ vendor/ web/` ✅

**② 排除 `models/`。**
`data/` 全量 111 MB，排除 44MB 的 ONNX 模型后压缩为 **35 MB**——与上游 `latest.zip`
的 34 MB 吻合，说明上游同样排除。同时排除 `oss/`（用户素材）、`logs/`、`temp/`、`*.sqlite`。

**③ 清单没有架构维度。**
`checkUpdate.ts` 用 `sourceData.find(d => d.type === platformType[process.platform])`
取安装包，每个平台只能挂一个链接。CI 里 Windows 取 x64、macOS 取 arm64；
其余架构的包仍上传到 R2，需用户从下载页自取。这是上游设计的固有限制。

| 项 | 说明 |
| --- | --- |
| **License 合规** | 补充协议明确禁止「删除或修改标识或版权信息」，且分发给 ≥2 个独立第三方需书面商业授权。对外出包前必须先与 HBAI-Ltd 确认 |
| `electron-builder.yml` | 改 `appId`、`productName`、图标。注意 `productName` 决定 userData 目录名，改了等于换数据目录 |

| 交叉架构的 sharp | workflow 已有针对 macOS x64 与 Linux ARM64 的 `npm install --force @img/sharp-*` 补丁步骤，fork 时别删 |

### 8.6 版本号规则

采用四段式 `MAJOR.MINOR.PATCH.BUILD`：前三段与上游 Toonflow 保持一致，
第四段是本仓的定制迭代号——上游未发新版时递增它，即可把自有修复通过增量包
推给已装机用户。

| 位置 | 取值示例 | 谁在用 | 约束 |
| --- | --- | --- | --- |
| `package.json` 的 `version` | `1.1.8` | electron-builder 命名安装包 | **必须是合法 semver（三段）** |
| Git tag | `v1.1.8.1` 或 `v1.1.8.1-ovj-20260904-18e15e4` | 人看 | 前三段必须等于 `package.json` |
| `__APP_VERSION__` | `1.1.8.1` | 客户端自报版本 | 编译期由 `APP_VERSION` 环境变量注入 |
| `update.json` 的 `version` | `1.1.8.1` | 客户端比对 | 与 `__APP_VERSION__` 同源 |

tag 的 `-ovj-日期-commit` 后缀沿用 new-api 仓库的下游标识风格，纯粹给人看，
CI 会剥掉后只取数字部分。

#### 为什么四段号不能写进 package.json

electron-builder 校验 semver，会直接构建失败：

```
⨯ Invalid version: "1.1.8.1"   at fixVersionField (app-builder-lib)
```

（`yarn install` 反而能通过，所以这个问题只在打包阶段暴露。）
因此 `scripts/build.ts` 支持用 `APP_VERSION` 覆盖注入值，
`package.json` 保持三段供 electron-builder 使用。

#### CI 如何保证两边一致

`release.yml` 的 `prepare` job 集中解析版本号，四个下游 job（三个平台构建 +
`publish-r2`）都通过 `needs.prepare.outputs.app_version` 消费同一个值。

**这一点不能省**：安装包里的 `data/serve/app.js` 和增量包 `latest.zip` 里的
是同一个文件的两次构建。若只给 `publish-r2` 传 `APP_VERSION`，安装包会烘焙
三段版本 `1.1.8` 而清单写 `1.1.8.1`，用户装完立刻被提示更新到自己刚装的版本，
白下一次 35 MB 增量包。

`prepare` 还会做两道校验，不通过直接中止发布：

- tag 版本号必须是 `X.Y.Z` 或 `X.Y.Z.N` 纯数字
- 前三段必须与 `package.json` 一致（否则安装包文件名与清单 URL 对不上，
  发出去的 `update.json` 全是 404）

#### ⚠️ 首次发版的引导约束

四段号的比较逻辑（`parseVersion` / `diffSegment`）位于
`src/routes/setting/about/checkUpdate.ts`，它会被编进 `data/serve/app.js`，
**随增量包下发**。这意味着：

> 装着旧版客户端的用户，其 `app.js` 里仍是只看前三段的老逻辑
> （`taggerList[2] > currentVersionList[2]`）。清单写 `1.1.8.1` 时，
> 老逻辑算 `8 > 8` = false，**不会提示更新**——新比较逻辑因此永远送不到。

所以如果将来存在装着旧比较逻辑的客户端，**首个自建版本必须抬 PATCH 位**
（如 `1.1.9`）才能被老逻辑识别并下发；此后的 `.BUILD` 递增才对热更新用户生效。

本仓截至文档撰写时 release 数与 tag 数均为 0，不存在旧客户端，
首版可直接用四段号。

#### 递增示例

```
上游 1.1.8  →  本仓基线 1.1.8
   自有修复  →  1.1.8.1
   再修      →  1.1.8.2
上游发 1.1.9 →  同步后 1.1.9（package.json 一并改）
   自有修复  →  1.1.9.1
```

MINOR / MAJOR 跟随上游抬升时，`.BUILD` 归零即可——前三段变大天然领先。
