## 一分钟版

```bash
yarn lint                              # 类型检查
git commit -am "fix: xxx" && git push  # 提交并推送
yarn release                           # 自动算版本号 → 确认 → 打 tag 推送
```

约 12 分钟后：GitHub Release 发布完成，R2 上的 `update.json` 更新，
已装机用户通过约 35 MB 的增量包自动热更新。

进度查看：<https://github.com/reputationly/Toonflow-app/actions>

## 版本号规则

四段式 `MAJOR.MINOR.PATCH.BUILD`：**前三段与上游 Toonflow 一致，第四段是本仓的定制迭代号。**

| 位置 | 示例 | 谁在用 | 谁来维护 |
| --- | --- | --- | --- |
| `package.json` 的 `version` | `1.1.8` | electron-builder 命名安装包 | **你手动改**（仅在同步上游时） |
| Git tag | `v1.1.8.3` | 触发 CI、人看 | `yarn release` 自动生成 |
| `__APP_VERSION__` | `1.1.8.3` | 客户端自报版本 | CI 编译期注入 |
| `update.json` 的 `version` | `1.1.8.3` | 客户端比对判断是否更新 | CI 生成 |

### 两条约束（都会导致构建失败或静默失效）

**① `package.json` 必须是三段合法 semver。**
electron-builder 校验 semver，写成 `1.1.8.1` 会直接失败：

```
⨯ Invalid version: "1.1.8.1"   at fixVersionField (app-builder-lib)
```

所以四段号只存在于 tag、`__APP_VERSION__` 和 `update.json` 里。

**② 版本号必须是纯数字。**
`checkUpdate.ts` 用 `parseVersion` 逐段解析比较，任何非数字后缀都会被当成 `0`。
若沿用 new-api 的 `v0.13.2-ovaijisuan-20260903-6e9f99b1` 那种风格直接喂给清单，
客户端会**静默地永远收不到更新**（不报错、不提示）。

> tag 本身可以带下游标识——`v1.1.8.3-ovj-20260905-48137e6` 也是合法的，
> CI 会剥掉 `-` 之后的部分只取 `1.1.8.3`。但 `yarn release` 生成的是简洁形式。

### 更新类型如何决定

`checkUpdate.ts` 逐段比较客户端版本与清单版本，取**首个不同的段**：

| 首个不同段 | 行为 |
| --- | --- |
| MAJOR / MINOR | 提示用户去浏览器下载安装包，**不自动装** |
| PATCH / BUILD | **自动热更新**：下载 `latest.zip` → 覆盖 `data/` → 重启 |

远端版本比本地旧时不做任何提示（不会降级）。

## 发版流程

### `yarn release`

```bash
yarn release          # 交互确认后发布
yarn release --dry    # 只打印将要做什么，不实际操作
yarn release --yes    # 跳过确认
```

输出示例：

```
  上游基线    1.1.8   (package.json)
  已有迭代号  1, 2
  ────────────────────────────────
  即将发布    v1.1.8.3
  提交        0fdc4a2  feat(release): 新增 yarn release 自动递增定制迭代号
  分支        master

  确认发布 v1.1.8.3？(y/N)
```

### 三道前置检查

tag 指向当前 HEAD，所以 CI 检出的代码必须与你本地一致。不满足会直接中止：

| 检查 | 拦住的问题 |
| --- | --- |
| 工作区必须干净 | 改了没提交就发版，CI 拿到的是旧代码 |
| 本地分支与远端同步 | 本地领先未推送，tag 指向远端不存在的提交 |
| tag 不得已存在 | 手滑重发（会提示删除命令） |

### CI 做了什么

```
prepare (解析并校验版本号，约 10s)
   ├─ build-Windows  x64 / ARM64      ┐
   ├─ build-macOS    arm64 / Intel    ┘ 并行，约 8~10 分钟
   ├─ publish-r2     打增量包 → 生成清单 → 传 R2 → 回读校验 → 清理旧版本
   └─ release        发 GitHub Release（镜像备份，客户端不读它）
```

`prepare` 集中解析版本号供所有下游共享。**这不能省**——安装包与增量包里的
`data/serve/app.js` 是同一文件的两次构建，两边 `__APP_VERSION__` 不一致的话，
用户装完会立刻被提示更新到自己刚装的版本。

### 产出

| 位置 | 内容 |
| --- | --- |
| `https://aijisuan.kdns.fr/update.json` | 版本清单，客户端固定读这个，`no-cache` |
| `https://aijisuan.kdns.fr/<版本>/latest.zip` | 增量热更新包，约 35 MB |
| `https://aijisuan.kdns.fr/<版本>/*.exe` `*.dmg` | 4 个安装包（win x64/arm64、mac arm64/x64） |
| GitHub Releases | 同样 4 个安装包，镜像备份 |

清单里每个平台只挂一个链接（`checkUpdate` 按 `process.platform` 取单项，
没有架构维度），Windows 取 x64、macOS 取 arm64。其余架构的包仍在 R2 与
GitHub Release 上，用户可自取。

### 存储与清理

每版约 1.05 GB（4 个安装包 247+249+266+280 MB + 增量包 35 MB）。发布成功后自动清理，
**保留最近 3 个版本**，占用稳定在约 3.2 GB（R2 免费额度 10 GB）。

按「数量」而非 R2 生命周期规则的「天数」保留——后者若长期不发版，
会把当前正在服役的版本一并删掉。

改保留数量：`release.yml` 里 `KEEP: "3"`。

> Linux AppImage 已不再构建：每版占 967 MB（全部产物的 47%），
> 而 Docker / PM2 服务器部署跑的是 Node 后端，并不需要 AppImage。

## 发版前的验证

### 空跑

正式发版前想验证分发链路，用空跑（约 2 分钟，不碰生产 `update.json`）：

**GitHub → Actions → Build and Release → Run workflow**
→ Use workflow from `master` → 勾选「空跑」→ Run

空跑会：跳过平台构建 → 打增量包 → 生成清单 → 传到 `dry-run/` 前缀
→ 从公开域名回读校验 → 删除 `dry-run/` 产物。

**必须勾选那个复选框**。不勾的话会跑完整的平台构建（十几分钟），
但因为不是 tag 推送，`publish-r2` 与 `release` 都不满足条件，最后什么也不发布。

### 本地检查

```bash
yarn lint             # 类型检查
yarn build            # 确认 esbuild 能产出 data/serve/app.js
yarn release --dry    # 确认版本号算得对
```

## 同步上游后发版

上游 Toonflow 发新版时：

```bash
# 1. 合并上游改动（按需处理冲突）
git fetch upstream && git merge upstream/master

# 2. 手动把 package.json 的 version 改成上游版本号，如 1.1.9
#    这是唯一需要手改版本号的地方

# 3. 前端若有改动，需重新构建并同步产物
#    cd ../Toonflow-web && yarn build && cp -r dist/* ../Toonflow-app/data/web/

# 4. 若改过 data/vendor/*.ts，必须重新生成 vendor.json
yarn vendor2json && mv data/vendor/vendor.json src/lib/vendor.json

yarn lint && git commit -am "chore: 同步上游 1.1.9" && git push
yarn release          # 自动发 v1.1.9.1（新基线下无 tag，从 .1 开始）
```

### ⚠️ 两个容易漏的点

**`vendor.json` 必须重新生成。** 内置供应商的注册源是 `src/lib/vendor.json`
（`fixDB.ts:165` 从它自动注册），**不是** `data/vendor/*.ts`。只改后者的话，
新用户装上不会有你新增的供应商。

注意 `yarn vendor2json` 的输出路径是 `data/vendor/vendor.json`，
而消费方是 `src/lib/vendor.json`，**需要手动搬运**（上游遗留的路径不一致）。

**热更新会覆盖整个 `data/`**，包括 `vendor/`。用户在设置中心手工改过的供应商代码
会被下一次增量更新还原成仓库里的版本。

## 基础设施

### Cloudflare R2

| 项 | 值 |
| --- | --- |
| Bucket | `ovaijisuan`（APAC） |
| 自定义域 | `aijisuan.kdns.fr`（活动、已启用） |
| 公共开发 URL | 保持**禁用**（有自定义域就不需要，开着多一个未加固入口） |
| CORS | **不需要配**，`checkUpdate` 和 `downloadApp` 都是 Node 后端发起的请求 |
| 默认存储类 | 应为「标准」，不要用「不常访问」（有取回费与最短存储期） |

建议加一条生命周期规则：清理 ≥7 天的未完成分段上传，避免碎片静默计费。

### GitHub 配置

仓库 `reputationly/Toonflow-app` → Settings → Secrets and variables → Actions：

| 名称 | 类型 | 说明 |
| --- | --- | --- |
| `R2_ACCOUNT_ID` | Secret | Cloudflare 帐户 ID |
| `R2_ACCESS_KEY_ID` | Secret | R2 API 令牌的**访问密钥 ID**（不是「令牌值」） |
| `R2_SECRET_ACCESS_KEY` | Secret | **机密访问密钥**，只显示一次 |
| `R2_BUCKET` | Secret | `ovaijisuan` |
| `R2_PUBLIC_BASE` | **Variable** | `https://aijisuan.kdns.fr`，不带结尾斜杠 |

`R2_PUBLIC_BASE` 放 Variable 而非 Secret：它是公开域名不敏感，
放 Variable 的好处是 Actions 日志里能正常显示，出问题时一眼看得到拼出的 URL。

R2 令牌权限应为**对象读和写** + **仅 `ovaijisuan` 存储桶**，
不要用「管理员读和写」或「所有存储桶」。

### 客户端指向

`src/routes/setting/about/checkUpdate.ts` 顶部：

```ts
const DEFAULT_MANIFEST_URL = process.env.UPDATE_MANIFEST_URL || "https://aijisuan.kdns.fr/update.json";
```

支持 `UPDATE_MANIFEST_URL` 环境变量覆盖，便于私有化部署各自指向自己的分发桶。

## 故障排查

### 构建失败但 R2 没被污染

这是**设计如此**。`publish-r2` 的条件里有 `!contains(needs.*.result, 'failure')`，
任一平台构建失败就跳过发布，生产 `update.json` 保持原样。

不这样做的话会出现：清单说有新版本（patch 位还会立刻热更新），
但 GitHub Release 是空的，且失败平台的用户点更新会撞上
`400 该源暂无适用于当前系统的安装包`。

修好问题后重新发即可。若要复用同一个版本号：

```bash
git push origin :refs/tags/v1.1.8.3   # 删远端 tag
git tag -d v1.1.8.3                   # 删本地 tag
yarn release                          # 重新发
```

### 版本号校验失败

```
::error::tag 前三段 1.2.0 与 package.json 的 1.1.8 不一致，请先同步 package.json
```

安装包文件名用 `package.json` 的版本，清单 URL 用 tag 的版本，两者对不上会导致
发出去的 `update.json` 全是 404。改 `package.json` 后重新提交再发。

### 历史踩过的构建问题（已修复，供参考）

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| Windows ARM64 `Could not find any Visual Studio installation` | `sqlite3` 无 arm64 预编译包需 node-gyp 现场编译 | 移除死依赖（项目用 `better-sqlite3`，`sqlite3` 源码零引用）。但仍须保留在 `scripts/build.ts` 的 `external` 列表——knex 的 sqlite3 方言含静态 `require('sqlite3')` |
| macOS Intel `ModuleNotFoundError: No module named 'distutils'` | `lzma-native` → node-gyp 9.4.1 用了 Python 3.12 已移除的 `distutils` | 移除冗余的 `electron-rebuild`（electron-builder 已自带 `@electron/rebuild`，且不依赖 `lzma-native`） |

### 客户端收不到更新

按顺序排查：

1. `curl -s https://aijisuan.kdns.fr/update.json` —— 清单里的 `version` 对吗
2. `curl -sI <清单里的 zip URL>` —— 返回 200 吗
3. 清单版本是否**严格大于**客户端版本（相等或更小都不会提示）
4. `curl -sI https://aijisuan.kdns.fr/update.json | grep -i cf-cache-status`
   —— 应为 `DYNAMIC`。若是 `HIT`，说明 Cloudflare 缓存规则盖掉了 `no-cache`，
   需在 CF 上为该路径加缓存绕过规则
